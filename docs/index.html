Refresh / Content Opportunity Scoring

Which Pages Decline First? Scoring Content for Refresh Review

Reviewers can't manually check every page for search-visibility decline, so this project asks: which pages should be reviewed first, given limited capacity? Using 135,113 content pages from FlyRank's production search warehouse, a Logistic Regression model was trained on twelve pre-decision features and validated with a client-grouped split to prevent memorization. Scored on the same held-out pages, the model measured Precision@50 of 0.50 against a hand-written baseline rule's 0.12 — roughly 4x the baseline, and clearly above the 0.24 base rate. This is decision-support for a human reviewer, not an automated action.

01 — Introduction

The problem: too many pages, too little review time

A content team with thousands of published pages cannot manually check each one for search-visibility decline. Without prioritization, a reviewer finds candidate pages by ad hoc browsing, or worse, by whichever page happens to come up in conversation. Real declines can go unnoticed for a full review cycle simply because no one was looking.

This project ranks the full page inventory so a reviewer's limited time goes to the pages most worth a look first. The output is a scored, reason-coded queue, meant to be read by a human before any action is taken, never applied automatically.

Who acts on this: a content reviewer or SEO strategist, working through the top of the ranked queue each review cycle. Cost of a wrong call: a false positive wastes review time; a false negative lets a real decline go unaddressed until the next cycle. Neither is severe on its own, which is why this stays decision-support, not automation.

02 — Data

Data

Results in this paper come from the FlyRank internship warehouse release (FlyRank/internship-warehouse), export date 2026-07-03, with a 3-day freshness lag so daily facts stop at 2026-06-30. Two tables were used: daily GSC/GA4 performance facts, and a content-properties dimension table. All identifiers are pseudonymized hashes provided by the release itself; no client names, domains, URLs, or raw search queries appear anywhere in this project.

Windows

A prior 30-day window (2026-01-31 to 2026-03-01) and a current 30-day window (2026-03-02 to 2026-03-31), relative to a fixed decision date of 2026-03-31. Every feature is computed strictly before this date.

Filters and exclusions

  • Pages restricted to gsc_data_available = TRUE and a nonzero prior-30-day impression baseline, since a percent-change label is undefined without one.
  • Content restricted to published, non-deleted pages.
  • After filtering: 135,113 pages across 42 clients.
  • FlyRank's own product flags (an internal health score, the LLM provider/model used to generate a page) were excluded entirely — using an existing system's decisions as model inputs teaches the model that system's past behavior, not the underlying world.
An earlier 30,000-row anonymized starter slice was used only for early scoping (Weeks 1-2), to validate the workflow before committing to this lane. Every result reported in this paper comes from the full warehouse pull above, not the starter slice.

03 — Methodology

Methodology

Label

is_declining_label = 1 if a page's current-30-day GSC impressions are more than 20% below its prior-30-day impressions, else 0. This is a same-portfolio, same-metric comparison — not a claim about search-algorithm behavior. Base rate: 0.24.

Features

Twelve features, each knowable strictly before the decision date: prior-30-day impressions, clicks, CTR, and average position; content age in days; days since last optimized and whether the page had been optimized at all (filtered to exclude any optimization after the decision date); word count and whether it was recorded; and one-hot content type (comparison / feedly / keyword article).

Baseline

A hand-written rule, not a naive majority guess: a page is flagged STALE_AND_UNDERPERFORMING when it is both aging (3-12 months old) and its click-through rate falls under 50% of its position-tier peer median; CTR_BELOW_POSITION_PEERS for the CTR gap alone; STALE_ONLY for age alone; NO_FLAG otherwise. This is the bar the model has to clear to earn its added complexity.

Validation design

GroupShuffleSplit by client, 70/30, so no client appears in both train and test. This matters more than it sounds: a random split let the same client's pages leak across train and test, and Precision@50 on that random split measured 0.86 — a number that collapsed to 0.50 once client overlap was removed. The gap is memorization, not skill, and the grouped-split number is the one this paper reports as the result.

Leakage checks

No column from the label's own current-30-day window appears in the feature set; no FlyRank product flag appears in the feature set; every feature's timeline was checked against the decision date. As a direct test of the check itself, adding current-window impressions back into the honest feature set pushed Precision@20/@50 from 0.35/0.50 to a perfect 1.00/1.00 — confirming the leakage test correctly detects a real leak rather than silently passing one.

The baseline rule scoring below the base rate is a real finding, not an error — it was built to flag staleness plus a CTR gap, a different pattern than the specific 30-day impression-decline label it's scored against here. The model's largest coefficients (content-type indicators) lean on a signal the rule's formula doesn't use at all, consistent with the two methods capturing different, only partly overlapping patterns. Across the full ranked portfolio, the model's top 1,000 predicted pages and the rule's top-priority reason code agree less than half the time — 53% of the model's top 1,000 rows carry NO_FLAG under the rule.

05 — Limitations

What this work cannot claim

  • Single decision date. Every result comes from one snapshot, 2026-03-31. Optimization-history features are structurally empty at this date — no warehouse optimization predates it — so their real value is untested.
  • Validated on 13 clients. The one honestly validated number in this paper (Precision@20/@50) comes from a 13-client holdout. It does not guarantee the same precision on a materially different client base.
  • Association, not causation. The model measures which pages are associated with decline. It says nothing about whether refreshing a flagged page would cause a recovery — that would require a controlled experiment this data cannot provide.
  • Not a claim about Google's ranking algorithm. Every feature is an observed outcome (impressions, clicks, position), never an internal signal.
  • The label is a proxy, not ground truth. A 30-day drop can reflect a genuine decline, seasonality, or traffic shifting to a sibling page. The model cannot tell these apart; a human reviewer is expected to.
  • Decision-support only. Every recommendation here is intended for human review before any action. Nothing in this project is built to run unattended.

06 — Ranked Recommendations

The action playbook

Each page in the full portfolio gets a model score (probability of decline) and a reason code from the baseline rule, which maps to a recommended action:

STALE_AND_UNDERPERFORMINGContent fix — top priority
CTR_BELOW_POSITION_PEERSSnippet fix — title/meta rewrite
STALE_ONLYMonitor — low urgency
NO_FLAGNo action
Read the reason code as a second signal, not an explanation. The model's ranking and the rule's reason code frequently disagree (see Results). A reviewer should check both, not assume one justifies the other.

Cost / value

At measured Precision@50 = 0.50, a reviewer working the top 50 of the model-ranked queue should expect roughly half to be genuine declines. Precision beyond depth 50 has not been measured — deeper queue use is a judgment call, not a validated recommendation.

What should never be automated

  • Auto-publishing content changes from a score alone.
  • Auto-deprioritizing NO_FLAG pages — no rule triggering isn't the same as "this page is fine forever."
  • Client-facing language stating a page "is declining" as settled fact, rather than "flagged for review."
